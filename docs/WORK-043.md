## 审计结果与待决定的问题

654,366次实际引擎求值，按最高合法槽位及相关晶核数量组合搜索，低阶不会提高这些单项上限。Ω装备8槽、Ω书6槽。普通／深层的最大HP为53.3938769／144.7076581，裸攻击60／248，满冷却暴击加剑爆裂103.9102597／399.6，额外防护F为16.3796811／654.25，最高匹配方块挖速209.1526601／880。数值不是一套配置同时达到；不含药水、吸收、盾牌、持续伤害或额外原版甲防护。

1. **深层防护公式不单调。**头盔空槽案例：U防护7.9、Q=0、F11.9；添界限Lv1使Q=0.2却F7.36。四件都有对应反例。分段Q=0／非0会丢失序数基础防护；建议后续统一 `extra=0.25U+0.25Q(1+2U)`，本轮未改公式或峰值。
2. **手稿固有b压过空集Lv1耐久。**空白四档书已5／9／13／17倍，最高书再加空集Lv1只提升17→20。建议独立降低b的省耐久权重，保留晶核本身的系数；未应用。
3. **果糕基值一致不等于最终HP一致。**深层固有b已放大果糕，没有序数时6果糕也108.182HP。最高HP配装为3果糕3＋3序数4；如希望最终HP也里外相同，需再改通用生命公式。
4. **F与W峰值不可直接相乘。**同甲槽位竞争已进行联合搜索，深层靴子的合法最大F×W为308,754.56，使用F565.6、W545.8885，而非把654.25和547.60硬乘。各部位联合最优也不是同一套甲。

这些是审计发现，不是已授权的重新平衡结果。数值页保留现有公式，提供反例配置链接，供用户决定下一步。

## 模拟器采用的新需求（主 Mod尚未实施）

- 用户最新将镐额外开采移到序列晶核，将镐时运移到分枝芽核，并明确剑抢夺与时运一起归分枝。两者沿用II／IV／VI（对应晶核Lv1／2／3），同一来源多颗取最高；适用原版附魔独立相加，序数装备本身仍不可附魔，手稿不提供时运／抢夺。
- 序列镐额外开采沿用原分枝规则：普通单颗1／2／3格，多颗floor(sqrt(sum(level²)))；深层单颗1／4／9格，多颗sum(level²)，不因换晶核而另设倍率。
- 用户确认精准采集归时运一侧，即分枝芽核镐，Lv1即解锁。在强化台界面增加独立“精准采集”开关，选择保存在镐上：默认关闭按时运结算，开启按精准采集结算且不应用该次时运。切换不拆晶核、不消耗材料；移除最后一颗分枝时不再启用精准。序列额外开采也遵循同一镐的当前采集模式，不能通过精准绕过挖掘硬度、工具资格或天然稀有物稳定采集条件。此开关不用于手稿或剑；本轮在模拟器实现，游戏强化台未改。
- 用户最新重新确定序列手稿为等价原版效率 II／IV／VI（对应晶核Lv1／2／3），覆盖此前“手稿不加挖速”的讨论限制。不能恢复旧分枝手稿的倍率挖速。新效率暂按同源最高／与原版取max，然后加e²+1，再由通用项放大；最终平衡仍可调整。
- 原移动整套为Lv1每颗跳高+1格、摔落伤害乘0.25（防摔不重复乘算）；Lv2慢速飞行、免疫摔落；Lv3创造式飞行、免疫摔落及飞墙伤害，深层冲刺水平和垂直均为普通飞行的8倍。Lv1跳跃可与高阶共存，Lv3飞行覆盖Lv2。此前归分枝，用户要求飞行另找归属后建议整套移到界限，本轮模拟暂采用此归属；头盔水下呼吸已明确移到紫菜。

## 原版行为核对

本地Minecraft26.2的时运与抢夺定义 `max_level=3` 是常规获取上限。物品附魔组件可存更高等级，运行时的矿物额外掉落与抢夺函数直接读取等级，不把6截到3；6级可真实生效。当前Mod先求晶核总和，再与附魔取较大值，这仍是旧实现，不代表上述新需求已生效。

普通受击时，原版对每件护甲分别扣 `floor(max(1,D/4))` 耐久；D是进入护甲减伤前、已处理难度和格挡等的伤害。10HP通常每件扣2，100HP每件扣25，并非四件分摊。随后才进行护甲、抗性／附魔保护及生命处理，所以原版高减伤不会相应减少基础磨损。绕过护甲的伤害来源通常不走这次磨损；火中接触和熔岩会走，持续燃烧、摔落、音爆及虚空等跳过。当前省耐久在每点损耗上按概率处理，但尚未增加本轮“受击磨损随防护衰减”的规则。

核对依据：本地 `C:/Users/sigmoid/.gradle/caches/fabric-loom/26.2/minecraft-merged.jar` 的 `ItemEnchantments.Mutable`、`ApplyBonusCount`、`EnchantedCountIncreaseFunction`、`LivingEntity.getDamageAfterArmorAbsorb`／`doHurtEquipment`、`Player.actuallyHurt`，以及包内 `data/minecraft/enchantment/fortune.json`／`looting.json` 和 `data/minecraft/tags/damage_type/bypasses_armor.json`。本轮不启动游戏。

## 自建服务器可行性（本轮仅只读审计）

当前Mod为双端环境，main/client入口与客户端Mixin分离，公共代码未发现客户端导入。服务端和玩家使用同一Minecraft目标及同一主Mod版本，并安装对应Fabric API；26.2配置使用Java25、Fabric API0.153.0+26.2和Fabric Loader至少0.19.3。手稿和传送判定在服务端按玩家处理，不用把客户端画面Mod整包复制到服务器。

现有0.3.11真实验证是独立隐藏fo262中的集成服务器路径，并非专用服务器冷启动或真实多人长期负载验证。本轮未启动服务器或游戏；未来开服前需专用服启动与至少双客户端回归。主要未测项是多人高速探索新区块的生成负载，以及第三方反作弊对飞行／触距的兼容。不能据此承诺人数上限或特定内存用量，也不把客户端晶核动画算成服务端渲染负载。依据见README.md、ports/targets.json、src/main/resources/fabric.mod.json、ports/common.gradle、ports/common/main/dev/googology/mining/ManuscriptEffects.java、docs/WORK-041.md及docs/VALIDATION.md。
